# ADR 0025: The map is vendored to plugins behind an opt-in `--with-map` flag, with three sub-features left out

**Status:** Accepted

## Context

Plugins need the same interactive map the host uses (`SoilhiveMap`) — search, draw, H3-cell selection, style switching — the same kind of prep work we already did for `UI/`. Unlike `UI/`, though, `SoilhiveMap` didn't start out self-contained ("its own icons, its own prop types, relative imports only" ) in two separate ways:

1. **Host context coupling.** It read `AvailabilityMapContext` and `AvailabilityContext` directly via `useAvailabilityMap()`/`useAvailability()`. A plugin route is a sibling of the Availability module, not a descendant — `useAvailability()` throws outside its provider.
2. **A heavier, less isolated dependency footprint.** The map needs `maplibre-gl`, `react-map-gl`, `@turf/turf`, `h3-js`, and friends — a meaningfully bigger bundle than anything vendored so far, not something every plugin should pay for by default. Three of its sub-features — the DAI overlay, the area-selection info card, the upload-a-polygon modal, and the map-style switcher — also each transitively pulled in something that can't or shouldn't be vendored at all:
   - **DAI** needs `useDai()` → `useApiQuery`, a host-only network hook tied to `AvailabilityContext`'s live filter session. There's no equivalent a plugin could have.
   - **`AreaInfo/`** (the desktop popup / mobile bar shown on selection) is the planned home of the `map-info-card` capability — it will eventually contain `mf.loadRemote()` logic to load a plugin's own contribution into the host's map. Vendoring it as-is would ship that future remote-loading logic inside every map-enabled plugin's own bundle — a plugin capable of loading and rendering other plugins.
   - **`UploadPolygonModal/`** and **`MapStyleSwitcher/`** both transitively need `components/Dialog/Dialog` → `primereact/confirmdialog`. `primereact` is explicitly excluded from plugins, and reaching it also means the global, unscoped `primereact` theme CSS (`styles/index.scss`'s `primereact/resources/themes/mira/theme.css` import, deliberately stripped out of a plugin's generated `index.scss` today) plus a hand-tuned `prime.react.override.scss` (permanently never-copied) that a plugin wouldn't inherit — real risk of visibly broken/unstyled dialogs, not just a bundle-size concern.

Additionally, `Map/`'s files reach outside their own folder via bare path aliases (`hooks/useDevice`, `assets/icons/*`, `types/backend`, `utilities/geo`, `components/UI/...`) that the plugin scaffold's build config doesn't define, and via relative imports that assume the host's deeper `src/components/Map/` nesting — neither resolves once flattened into a plugin the way `UI/` already is.

## Decision

**`SoilhiveMap` becomes a fully controlled component.** All state it used to read from `AvailabilityMapContext` is now passed in as a `selectionState` prop (shaped identically to `useAvailabilityMap()`'s return value, so the host can pass it straight through); DAI becomes an entirely optional `dai` prop group; a `children` slot (rendered inside the underlying `<Map>`, for content needing `react-map-gl`'s context) and a `footer` slot (rendered as a flex-sibling of `<Map>`, for content that doesn't) let a consumer layer its own UI on top. `AvailabilityMapContext`/`AvailabilityContext` themselves are untouched — `Availability.tsx` still ultimately owns and drives the same state, just via props instead of `SoilhiveMap` reading the context directly.

**Three sub-features move out of `SoilhiveMap` to host-owned composition, the same way, and are excluded from what's vendored:**

| Feature | Where it went | What a plugin gets instead |
|---|---|---|
| `AreaInfo/` (selection info card) | `Availability.tsx`, via `children`/`footer` | `PluginContext.mapSelection` (already existed) to build its own card |
| `UploadPolygonModal/` (toolbar's "upload via modal") | `Availability.tsx` owns the modal; `SoilhiveMapToolbar` gained an optional `onUploadClick` prop instead of importing the modal itself | `SoilhiveMapRef.onUpload` (drag-and-drop already uses this same path) + `onUploadClick` to supply its own upload UI |
| `MapStyleSwitcher/` (style picker) | `Availability.tsx`, via `children` | `currentMapStyleIndex` prop to build its own switcher |

None of this changes the host's behavior — each moved piece is the exact same component, just instantiated one level up.

**The map is vendored via the CLI behind an opt-in `--with-map` flag** (`frontend-scripts/soilhive-plugin/`). `syncMap.ts` vendors `frontend/src/components/Map/` (minus the three excluded subfolders, always-overwrite, same host-is-authoritative policy as `UI/`) plus the cross-cutting files it reaches outside its own folder (`DrawControl.tsx`, `hooks/useDevice.ts`, `configuration/layout.ts`, `utilities/{geo,geometry,map,simplifyGeometry,environmentVariables}.ts`, `types/backend.ts`, the icons it references), each nested under `Map/_shared/` rather than flat at the plugin root — so a plugin author scanning the tree can tell at a glance what's map-internal versus their own code, rather than finding map internals scattered across several unrelated-looking top-level folders. `styles/SoilhiveMap.scss` is the one exception: it stays flat at the plugin root, alongside the rest of `styles/`, unaffected by the `Map/_shared/` nesting. `copyEngine.ts`'s `SoilhiveMap.scss` block becomes conditional on an `allowMapAssets` option (`prime.react.override.scss` stays permanently blocked). `paths.ts`'s `resolveWithMap` detects a prior opt-in via `react-map-gl` already present in the plugin's dependencies, so `--with-map` only needs to be passed once — on first scaffold, or on a first retrofit — never again after.

**The plugin scaffold gains `assets`/`hooks`/`types`/`utilities`/`configuration` path aliases unconditionally** — for every plugin, whether or not it uses `--with-map` — mirroring how the `styles` alias was already added unconditionally for `UI/`'s sake. These remain available for a plugin author's own code, but `Map/`'s own cross-cutting files don't rely on them: every shape `Map/`'s own files use to reach them — a bare alias (`hooks/x`, `assets/icons/x`), a double-relative path (`../../utilities/x`, `../../types/x`), or a plain relative sibling import (`../DrawControl`) — is rewritten at sync time into a depth-aware relative path into `Map/_shared/` instead (`rewriteMapFileImports`). This still preserves the original retrofit guarantee: the rewrite only ever touches vendored *file contents*, never `rsbuild.config.ts`/`tsconfig.json`, so retrofitting `--with-map` onto an already-existing plugin still never needs to patch a dev's config. `components/UI/x` is rewritten the same way it always was, since `UI/` still sits flat at the plugin root — one level further out than `Map/`'s own cross-cutting files now are, hence the one extra `../`.

**Map/'s cross-cutting local files are an explicit, reviewed list, not a dynamic resolver** — unlike `scanUiDependencies`' dynamic *npm*-package scan (`packageJson.ts`), which stays justified because `UI/`'s external dependencies legitimately grow over time. `Map/`'s in-repo cross-cutting surface is small and doesn't change often; building a transitive-closure import resolver to auto-discover it would solve a problem this codebase doesn't have yet. `syncMap.test.ts` guards against silent drift instead: it re-scans `Map/`'s actual current imports and fails if a new double-relative, `components/UI/`, or `assets/icons/` reference shows up that the hardcoded list doesn't already account for. The npm-package side of Map/'s dependencies *is* scanned dynamically, same as `UI/`'s — `packageJson.ts`'s scanner was generalized to accept multiple directories/files and to recognize the app's path aliases (so `hooks/useDevice` isn't mistaken for an npm package literally named `hooks`), then pointed at the plugin's own already-vendored `Map/` + cross-cutting output.

## Considered options

- **Relax `primereact` exclusion instead of excluding `AreaInfo/`/`UploadPolygonModal/`/`MapStyleSwitcher/`.** Rejected for now — the cost (a global, unscoped theme CSS a plugin doesn't inherit correctly, a hand-tuned override file that's permanently never-copied, real risk of a visibly broken dialog) is disproportionate to what's gained for three narrow, replaceable pieces of UI. Left as an explicit future option below.
- **A dynamic transitive-dependency resolver for `Map/`'s local cross-cutting files**, mirroring `scanUiDependencies`. Rejected as solving a problem that doesn't exist yet — this is a small, stable, in-repo file set, not an evolving external surface. The explicit list + drift-detection test gets the same "don't silently go stale" property at a fraction of the implementation risk (no import-resolution edge cases, no extension/index-file resolution bugs to get subtly wrong).
- **Add the new path aliases only when `--with-map` is passed**, instead of unconditionally. Rejected — `rsbuild.config.ts` is dev-owned after the first scaffold, so this would leave no clean way to retrofit `--with-map` onto an existing plugin without either overwriting a dev's config or leaving the aliases missing.

## Consequences

- A `--with-map` plugin gets the full interactive map — search, draw, H3-cell selection, upload via drag-and-drop or its own UI, its own style switcher — but not, out of the box: the DAI overlay, the built-in selection info card, the built-in style-switcher UI, or the built-in upload-via-modal UI. Each of the latter three is buildable by the plugin itself using an already-exposed prop (`PluginContext.mapSelection`, `currentMapStyleIndex`, `onUploadClick` + `SoilhiveMapRef.onUpload`) — no capability is actually gone, just not pre-built.
- **Follow-up left on the table, not solved here:** a small, shared, `primereact`-free popup/modal component covering exactly what `MapStyleSwitcher` and `UploadPolygonModal` actually need (`visible`/`header`/`onClose`/`children`, optionally `closeOnOverlay` — neither uses `Dialog`'s buttons, `aria-label`, or transition options) would let both be vendored and let plugins get style-switching (and optionally upload-via-modal) without primereact. This is additive whenever it happens — the controlled props (`currentMapStyleIndex`, `onUploadClick`) this ADR introduces are exactly what such a component would consume; nothing here needs to change to add it later.
- `syncMap.ts`'s cross-cutting file list needs a manual update the next time `Map/` imports something new from outside its own folder. `syncMap.test.ts`'s drift-detection test catches this for the shapes it actually scans for — a new double-relative import, a new `assets/icons/*` reference, any `assets/images/*` import, or a `components/Dialog/Dialog` reference — but not every possible shape: a brand-new single-relative sibling file added directly under `components/` (the way `DrawControl.tsx` is today) isn't scanned for and would need to be caught in review instead. This scan also only covers `Map/`'s own *direct* imports, not the cross-cutting files' own transitive ones — `configuration/layout.ts` briefly looked dead by this measure alone (nothing in `Map/` imports it directly), when in fact `hooks/useDevice.ts` does via a plain `../configuration/layout`. A second drift test now re-scans the cross-cutting files' own relative imports against the same list, closing that specific blind spot.
- Every `--with-map` plugin now carries `maplibre-gl`/`react-map-gl`/`@turf/turf`/`h3-js`/etc. — a materially heavier dependency profile than a map-free plugin. This is why the flag is opt-in rather than default-on.
