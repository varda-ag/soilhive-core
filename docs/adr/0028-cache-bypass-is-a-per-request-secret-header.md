# Cache bypass is a per-request secret header, not a deployment-wide switch

ADR 0024 concluded that cold-cache numbers from a deployed environment "require `QUERY_CACHE_ENABLED=false` or a restart there, which is a deployment action. A third option was never considered: leave the inputs untouched and make the *request* opt out of the cache. `X-SoilHive-Cache-Bypass: <secret>` does that. The request's asset fingerprint is unchanged, so baselines stay meaningful, and nothing about the deployment changes, so real traffic keeps its cache while the measured requests do full work. This supersedes the final sentence of ADR 0024's warm-cache consequence; the rest of that ADR stands.

**Bypass means the ADR 0008 in-memory LRU only, and it means cache-transparent.** All three of ADR 0008's paths funnel through two functions in `utils/query-cache.ts` — `cachedCompute` (which `cachedQuery` and the DAI's manual key both call) and `InMemoryQueryResultCache.getFromCache`/`storeInCache` — so the bypass is two touch points and zero call-site changes. A bypassed request neither reads **nor writes**: the shared LRU is capped at 1024 entries with LRU eviction, so a read-only bypass would have a full perf run evicting real users' hot entries and reshaping a cache other clients share. Cache-transparent is also exactly what `QUERY_CACHE_ENABLED=false` means, which is the parallel ADR 0024 drew. The precomputed tables — `feature_dai_stats` (ADR 0009) and `user_geometry_subdivisions` (ADR 0006) — are explicitly **not** bypassed: they are the data model and the path production always takes, not a cache, and routing around them would measure a branch production never executes. Postgres `shared_buffers` and the OS page cache remain the dominant source of run-to-run variance and are unreachable from an HTTP header; a bypassed run is cold in the application, never cold in the database.

**The flag reaches the cache through an `AsyncLocalStorage` store**, following `utils/query-debug.ts`, which already proves a store opened in middleware is visible inside TypeORM's own cache callbacks. Code running outside a request — pg-boss jobs, startup, migrations — finds no store and therefore can never bypass by accident. `isQueryCacheEnabled()` could not have carried this: it is read once when the DataSource is constructed (`utils/data-source.ts`), so it is a process-lifetime decision by construction.

## The secret is the entire gate, and it is load-bearing

`/data-filters`, `/dai`, `/coverage` and `/soil-data` are unauthenticated, and the cache is what makes them survivable. An ungated bypass header would be an unauthenticated amplification vector: one loop forcing full spatial aggregates on demand. The header is therefore honoured only when its value matches `CACHE_BYPASS_SECRET`, and **fails closed** — where that variable is unset the header does not exist, so no environment has the capability until deliberately given it. Requiring a `SUPER_ADMIN` scope instead was rejected on measurement grounds rather than security ones: an authenticated request resolves entitlements (`x-entitlements-required`), and entitlement-gated queries have a different shape than the anonymous ones every existing baseline was recorded with.

Beyond the secret there is **no guard rail**, deliberately: no host allowlist and no confirmation prompt, both already rejected by ADR 0024 for baking environment names into the repo and breaking CI use. Holding the production secret is a stronger and more honest gate than a hostname check. The consequence is accepted explicitly: under bypass the database performs 100% of the work on every iteration of every row, so a bypassed run against production is a load-generating act, and the run banner says so.

A header, not a query parameter, is also forced by the code: `validateRequests: true` in `middlewares/openapi.ts` rejects undeclared query parameters, while undeclared headers pass through — so this needs no OpenAPI change, avoiding the objection ADR 0024 raised against a `/fingerprint` endpoint. Honouring the standard `Cache-Control: no-cache` was rejected outright: every browser hard-refresh sends it, which would reopen the amplification vector to anyone with F5, and there is nowhere in it to carry a secret.

## Consequences

- **A bypassed run is not comparable to a warm one, and the tooling must enforce that, not mention it.** `Fingerprint` gains an optional `cacheBypass` field — optional so `PERF_RUN_VERSION` stays at 2, following the `endpoint?` precedent rather than the version bump ADR 0024 rejected. `diff.ts` compares it with a `?? false` default so pre-existing files classify correctly, **and** `findLastTwoRuns` folds it into its pairing key beside the target. Without the pairing change, zero-argument `perf:diff` would pair a cold prod run with a warm prod run — same `baseUrl` — and report the bypass as a catastrophic regression. ADR 0024's own words apply: "a warning on a report you did not want is not a fix."
- **Silent non-honouring is the dangerous failure, and it is a precondition check.** A target whose secret is misconfigured, whose build predates this change, or that sits behind a proxy stripping unknown headers returns an ordinary 200 while the run records `cacheBypass: true` — every number wrong in the same direction, and pairable with genuinely bypassed runs. A 403 on a bad secret cannot detect the latter two cases. Bypassed responses therefore **echo** `X-SoilHive-Cache-Bypass: applied`, the runner verifies it on the untimed preflight, and its absence aborts before anything is measured, under the existing policy that only precondition failures abort a run.
- **The bypass is a cache control, not a perf-suite feature.** It is named for its effect so that a future second client does not have to send a header called `X-SoilHive-Perf`, and it is vendor-namespaced so no proxy, CDN or framework header can ever collide with it. It is the first custom header in the codebase and sets that convention.
