# Remote perf runs fingerprint the data via the API, not the database

The performance suite (`scripts/perf/runner.ts`) exists to compare latency across runs, which is only meaningful when the data did not change in between — so every result file embeds an environment fingerprint, and the runner **aborts** when it cannot read row counts from Postgres ("the fingerprint is what makes runs comparable"). Pointing the suite at a deployed environment via `PERF_BASE_URL` breaks that premise outright: the deployed database is not reachable from a developer machine, which is the whole reason for measuring the deployed API in the first place. We therefore added a second data fingerprint derived from one untimed `GET /datasets` — per dataset `id`, `n_observations`, `n_raster_layers`, `updated_at`, plus the dataset count — collected in **both** modes, and made `Fingerprint.db` optional so that a remote run simply carries no direct DB counts.

`GET /datasets` is a sound substitute because it is unauthenticated (so it needs no credentials the suite doesn't already lack) and `n_observations` is a stored column rewritten by the bulk-load `UpdateDatasetMetadata` job, so it moves whenever ingestion changes data volume — the same signal the raw row counts provided. It also covers exactly the right surface: the suite runs anonymously, so the datasets this call can see are precisely the datasets the measurement can reach.

## Considered options

- **Keep the hard DB requirement for remote runs** — rejected: not merely inconvenient but impossible, and the fallback of trusting `.env` to describe the remote environment is worse than no fingerprint. A `.env` pointing at the local Docker database while measuring QA would emit a confident fingerprint that is simply wrong, and `diff.ts` would report "no mismatches" for two runs against different data.
- **A `/fingerprint` endpoint that reports the server's own row counts** — rejected: a stronger signal, but it puts perf-tooling concerns into the production API surface and requires an OpenAPI change for something only this script consumes.
- **No data fingerprint at all for remote runs** — rejected for the same reason as the first option: `diff.ts` compares `db` by iterating the union of table keys, so two runs with no counts silently agree. False confidence is the failure mode we are guarding against, so absence must be reported explicitly, never inferred as agreement.
- **Bumping `PERF_RUN_VERSION`** — rejected: `diff.ts` hard-throws on a version mismatch, which would invalidate every accumulated baseline. Adding optional fields follows the precedent already set by `endpoint?` and `filterId?`.

## Consequences

- **Comparability is target-scoped.** The fingerprint records `baseUrl`, and runs against different targets are a fingerprint mismatch as real as a row-count change. Zero-argument `perf:diff` therefore pairs the newest run with the newest *older run against the same target* (a missing `baseUrl` classifying as the local managed run) instead of blindly taking the last two files — otherwise the default would diff a QA run against yesterday's localhost run.
- **`diff.ts` must report a missing `db` fingerprint as a mismatch line**, not skip it.
- **Remote runs measure a warm, shared, multi-node system, and this is accepted.** A Filter is deduplicated by canonical content identity (ADR 0007), so repeat runs get the *same* `filterId`, and the DAI's cache key is `dai:{filterId}:{bbox}:{resolution}` with a 12h TTL (ADR 0008) — a remote DAI or coverage row can therefore measure a cache lookup rather than a query, and consecutive iterations may land on nodes with different cache states. Cache-busting was rejected: the only lever is perturbing geometries, bbox or resolution, which changes the asset fingerprint and destroys comparability with every baseline — trading a documented limitation for a silent one. Cold-cache numbers from a deployed environment require `QUERY_CACHE_ENABLED=false` or a restart there, which is a deployment action, not something `npm run perf` should simulate.
- **The suite is not read-only against a shared environment.** `POST /data-filters` canonicalises geometries, persists `user_geometries` and drives subdivision precomputation, and the run warms caches other users share. This is documented rather than gated: no confirmation prompt (it would break CI use) and no host allowlist (it would bake environment names into the repo). Dedup bounds the footprint to one filter per asset/variant regardless of run count.
- **`PERF_BASE_URL` is read from the shell before `dotenv` loads `.env`, deliberately.** Every other knob may live in `.env`, but this one decides which system gets measured *and written to*; a forgotten `.env` line would silently point a run at the wrong environment. The read ordering in `runner.ts` is load-bearing, not incidental.
