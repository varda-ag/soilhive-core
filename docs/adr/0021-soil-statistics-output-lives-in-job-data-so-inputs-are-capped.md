# Soil Statistics output lives in job data, so the input is capped and the breakdown is truncatable

Soil Statistics are returned inside the pg-boss `job.data` jsonb and read back through `GET /jobs/{jobId}`, so the whole result has to stay small enough to be a column value and a single HTTP response. The output is a cross product — Aggregation Units × Datasets × Soil Properties × sampling years × depth intervals — so nothing about the *query* bounds it; only the inputs do. We therefore cap the number of Aggregation Units (env-configurable, default 200) and fail the job above it, and we truncate the finest output level rather than the headline one.

## Consequences

- **Units are capped and breaching it fails the job**, it does not silently trim the list. A run that quietly ignored 49 800 of 50 000 uploaded fields would be indistinguishable from one that worked. The cap is checked with `ogr2ogr -limit cap+1` *before* any geometry is written, so an oversized file costs nothing and leaves nothing behind.
- **Two output levels, and only the finer one degrades.** `L1` per (Dataset, Soil Property, Aggregation Unit) is always complete; `L4`, the same keys plus year and depth, is dropped **all-or-nothing per (Dataset, Soil Property) group** with `l4_included: false` recorded on each omitted group, and `truncated: true` on the result. A flat cut through a sorted cell list would instead lop off whichever Datasets sort last, producing output that looks complete for the early ones and empty for the late ones.
- The asymmetry is the point: **never silently drop user-supplied input, but derived detail may degrade.**
- **Per-cell bytes are spent only on what cannot be derived.** At the cell cap a cell's *key names* outweigh its data, so the shape is pared back on four rules: numbers are rounded to 3 decimals (float8 prints up to 17 significant digits, none of them meaningful for a soil measurement); a field with no value is absent rather than `null` or `[]`; derivable figures are left out entirely — the coefficient of variation (`stddev / |mean|`), the interquartile range (`p75 - p25`), and the histogram's bin boundaries (`min + i * bin_width`), which alone were the largest field in a cell at ten bins; and a breakdown cell drops `depth_min`/`depth_max`, which the L4 grouping makes identical to the cell's own key. Together, roughly a 25–50% reduction depending on how much of a cell is populated.
- **A breakdown of one cell is not emitted at all.** With a single (year, depth interval) partition that cell covers exactly the rows behind the unit's own statistics, so it repeats them field for field. The condition is the cell count, not the layer count: a survey that sampled one depth interval in one season at fifty locations produces fifty layers and still only one cell. The cells are excluded from the budget too, so they cannot push another group into truncation for output that is never produced.
- **A histogram is only emitted above 100 Observations**, and the threshold is applied in SQL so the bins of a cell that will not carry one are never fetched or held in memory. Below it the bins describe the sample, not the distribution. This is the one rule that discards information rather than repackaging it, and it is the reason the cheap L4 cell — a handful of Observations in one year and depth interval — is now cheap in the output too.
- Two consequences to hold on to: `bin_width === 0` stopped being a safe test for "every value identical" (a real width under 0.0005 rounds to 0 too), so that case is signalled by `counts` having a single bin; and absent-means-no-value applies everywhere *except* a breakdown cell's `year`/`min_depth`/`max_depth`, where `null` is the bucket's identity and is always written out.
- Single-dimension marginals (per year alone, per depth alone) are not emitted. They are not derivable from `L4` either — median and the histogram cannot be recombined from sub-groups — so adding them later means more computation, not more formatting.
- `overall` per (Dataset, Soil Property) is computed *before* units are fanned out, where each Observation appears exactly once, and therefore does **not** equal the sum of the per-unit counts whenever units overlap.
- If the cap ever needs to go away rather than up, the output has to move out of job data — the export job's pattern (write to storage, return a presigned `download_path`) is the way, and that is an API change, not a tuning change.

## Considered options

- **Pre-flight estimate and fail above a cell cap** — no truncation semantics to design and no misleading partial output, but a job that fails after the user has waited is worse than one that returns complete headline numbers.
- **Spill the JSON to storage like `export`** — removes the ceiling entirely and reuses existing machinery, at the cost of the result no longer being readable from `GET /jobs/{jobId}`.
