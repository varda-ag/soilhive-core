# Raster CRS stays native; only derived geometry and export output are reprojected

**Status:** Accepted — partially supersedes ADR 0025, which included an eager ingest-time warp to EPSG:4326.

Rasters are now stored and ingested in whatever CRS they arrive in — `checkFileFormat`/`convertRaster` still normalize format (COG) and units, but no longer warp for CRS. ADR 0025's eager warp to EPSG:4326 was lossy (resamples every pixel, once, irreversibly) and reprojected the whole raster regardless of how much of it any AOI or export ever touched, when none of the actual consumers need the *stored file* to be 4326 — only specific *derived outputs* do. So reprojection moved to exactly where each of those outputs is produced: footprint tracing and `raster_layers.bbox` always reproject to EPSG:4326 (`GdalCLI.transformPoints`/`gdaltransform`, batched rather than per-tile); export-time masking still builds its base mask in EPSG:4326, and `soilExportJob`'s `getMaskForLayer` warps a copy to each distinct layer CRS on demand (via `gdalwarp`, cached per CRS) so `RasterFileWriter`'s clip stays a same-CRS intersection; and `RasterFileWriter`/`GeoFileWriter` warp only the already-clipped export output, and only when the export explicitly requests a `target_crs` — with none given, raster exports keep the layer's native CRS and vector exports keep the DB's stored EPSG:4326, unchanged.

A layer's native CRS is carried end-to-end as its raw WKT (`files.metadata.wkt`), not just an EPSG code: a raster's projection may have no registered EPSG code of its own (e.g. a custom local projection), which PostGIS's `ST_Transform` requires but GDAL's CLI tools don't — they accept a raw WKT anywhere they accept `EPSG:n`, which is why mask/crop reprojection uses `gdalwarp`/`gdaltransform` rather than SQL. `GdalCLI.extractEpsgFromWkt` still derives a best-effort `epsg` label (filenames, logging, quick CRS-equality checks) but only from a depth-1 authority id on the CRS itself — a nested id (e.g. a projection parameter's own EPSG code) belongs to a different kind of object and can collide with a real, unrelated CRS elsewhere in `spatial_ref_sys`.

## Consequences

- A dataset's raster layers can have different native CRSs from each other now (ingest-time warping previously forced everything to EPSG:4326 regardless of source) — `exportRasterData` iterates layers individually, reprojecting and caching a mask per distinct CRS rather than warping everything upfront.
- Any code that reads a raster's geoTransform and treats it as degrees must check the CRS first — `computeGrid`'s tile sizing and `analyzeRasterMeta`'s bbox both had this exact latent bug, masked until now by the ingest-time warp always making it true. That check must key off whether the CRS is geographic, not merely whether an EPSG code was found — a custom/unregistered projection has no EPSG code either way but still isn't 4326.
- The export-time warp's resampling method (`-r near` vs `-r bilinear`) comes from `raster_layers.is_categorical`, persisted at ingest from the band mapping rather than re-derived at export time, since the band mapping isn't in scope there. The column defaults to `false` (continuous).
