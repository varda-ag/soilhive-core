# A Data Request is a bearer capability addressed by its Run's id

`POST /data-requests`, `GET /data-requests/{id}` and `DELETE /data-requests/{id}` (SP-5634) expose the `data-requests` queue as a resource of its own, and the resource they expose is the **Data Request** — the record of one Run's outcome — not the job that computed it. Three things follow from that, and all three are deliberate departures from how `/jobs` behaves:

- **One identifier.** `data_requests.id` *is* the pg-boss job id. The same id addresses the Run while its job record lives and the Data Request afterwards, so a caller polls, reads and destroys through one URL for the resource's whole life. pg-boss generates job ids with `gen_random_uuid()`, the same 122 unstructured random bits the `data_requests` default was chosen for, so nothing is given up by reusing it.
- **No owner.** The id is the whole of the permission. A token is read for entitlements when one is present — it is the only place the external entitlements endpoint is reachable, so it decides which Datasets the Run may touch — and is then never consulted again. `GET` and `DELETE` compare nothing against a **Subject**.
- **One door.** `data-requests` is removed from the `POST /jobs` discriminator, and `GET`/`DELETE /jobs/{jobId}` return `404` for a job on that queue.

The third exists because of the first two. `/jobs` enforces `created_by === subject` and its `DELETE` cancels without destroying anything; `/data-requests` opens for any bearer and its `DELETE` destroys the record. Leaving both doors open would let a caller defeat the destroy semantics by cancelling through `/jobs`, and would answer `401` at one door to the very bearer the other door is built for. Nothing had been deployed, so the type was removed rather than deprecated.

## Considered options

- **One id, bearer access, one door (chosen).** The identifier is the capability, which is what `CONTEXT.md` already said a Data Request was before any of this was built. It also makes the post-retention read work without an API change: the row takes over from the job under the same URL.
- **Two ids — a job id for progress, a separate Data Request id for the answer (rejected).** The honest version of "the job and the record are different things", and the only design that supports an *attenuated* share: hand out the read id without the cancel/destroy power. Rejected because it makes the common path two round trips and two things for a caller to keep — you cannot read your answer until you have polled the job to learn the second id — and because the resource a caller thinks in terms of is one request, not a job plus a record.
- **Token forbidden entirely (rejected).** The purest reading of "no token required", and it removes the question of what a token changes. It also permanently caps `/data-requests` at public Datasets, because a processor re-derives entitlements from `created_by ?? EVERYONE` and a tokenless submission has no Subject — so the product's own users would have had to fall back to `POST /jobs`, which this ADR then closes.
- **`DELETE` cancels only, rows expire by retention (rejected).** Safer against accidental destruction, and it keeps bearer ids read-only in effect. Rejected because a `DELETE` that leaves the record standing is false in the contract, and because a row with no owner and no delete path is unerasable by anyone — the only lever left would be a retention policy nobody has specified.
- **Keeping `/jobs` as a second, privileged door (rejected).** Sounds like a safe superset, but the two doors differ in *rules* rather than in capability, and the rules are contradictory rather than merely stricter.
- **Serving `soil-indexes` Runs from the same endpoint (rejected).** `CONTEXT.md` had claimed a **Soil Index** was the `data` half of a Data Request "whichever queue ran it". The code went the other way for a stated reason — a Soil Index Run's output grows with the **Aggregation Unit** count and would breach the payload ceiling of docs/adr/0021, so its scores are rows in `soil_index` keyed by `run`. The glossary was narrowed to match. `/soil-indexes` will mirror this design rather than share it.

## Consequences

- **Bearer capabilities do not attenuate.** Passing the id on so someone can read the answer also hands them the power to destroy it, irreversibly, with no audit trail beyond a log line. There is no read-only share, and adding one means the two-id design rejected above.
- **A caller's private data can be read by whoever they pass the id to.** A Run submitted with a token computes under that Subject's Entitlements; the resulting payload is then readable by any bearer. This is the definition of the resource, not a leak — but it means "share the link" and "share the data" are the same act, and it should be said in those words wherever the id is surfaced.
- **`created_by`, `isDataAdmin` and `isSuperAdmin` never cross the boundary.** `GET /jobs/{jobId}` returns them today inside `data`; the Data Request representation drops them, and the `request` jsonb is assembled without them. Getting this wrong writes the submitter's identity and privilege into a permanent row that anyone holding the id can read.
- **A cancelled Run must read as `404`, not as `cancelled`.** `DELETE` deletes the row, but the pg-boss job survives in `cancelled` state until retention, so a `GET` that trusted the job would keep answering `200` for a resource the caller destroyed. `cancelled` is consequently a state no client can ever observe.
- **A Run that had already terminated cannot be cancelled, so `DELETE` deletes its job row.** pg-boss's `cancel` is `UPDATE ... WHERE state < 'completed'`; on a `completed` or `failed` job it silently matches nothing, and hiding the state instead - the reading above - would only move the problem, because the job is then the live half of a resource whose record is gone. Nothing is running to be stopped at that point, so the job is removed outright and the Data Request has no half left anywhere. The asymmetry is deliberate: a job that is still cancellable is cancelled and *kept*, because the worker learns it was cancelled by reading that job's own state.
- **Every terminal outcome is recorded, and only a cancellation leaves nothing.** A Data Request is written for a failure as well as for an answer, so "why did my request produce nothing" survives the job record; `data` is nullable and `status` (`pending` / `running` / `completed` / `failed`) carries the outcome. The write happens in `processDataRequest`, the only entry point specific to this queue — `processRun` is shared with `soil-indexes` and stays ignorant of the table. A cancelled Run returns from `processRun` with no payload and no throw, and that absence *is* the signal not to write. It is not the whole of the race, though: the cancellation checkpoints are not the last thing a Run does, so a `DELETE` landing after the final one leaves the processor about to insert a row for a record already destroyed - and that row would be permanent, since the job is `cancelled`, reads therefore fall through to the record, and the `DELETE` that would have swept it has already returned. The insert carries the check itself, conditioned in the same statement on the job existing and not being cancelled, which narrows the window to the write.
- **The row must be self-sufficient, because the job is the part that expires.** `request` carries the resolved `units[]`, `derived_filter_id` and `unit_count` alongside what was submitted: `UnitStatistics.unit_id` is a UserGeometry uuid, and without the unit labels and areas the permanent payload is a table of identifiers nobody can interpret. `created_at`, `completed_at`, `status` and `message` become columns for the same reason — after 30 days there is no job to take them from. The entity's "deliberately not a BaseTable" note no longer applies to the timestamps.
- **A failure can arrive before anything is resolved**, so the row has to be writable with `units: []` and `derived_filter_id: null` — `RUN_TOO_MANY_UNITS` throws during unit resolution and an unknown `filter_id` throws before it.
- **Status uses a domain vocabulary, not pg-boss's.** `pending` / `running` / `completed` / `failed`, lowercase. Deliberately *not* `IngestionStatus`'s `PENDING`/`ONGOING`, which is a Dataset's ingestion lifecycle and would give `ONGOING` two unrelated meanings; and deliberately not `created`/`active`, which are queue-implementation words in a resource that has otherwise had its queue leakage removed. `completed` and `failed` are spelled as the frontend already reads them for export jobs.
- **`anonymous` is gone from this body.** It was documented as "set to true to allow access without authentication" and enforced nowhere — the only code reading it *rejects* it for the admin job types. Anonymity was always decided by whether `created_by` ended up null.
- **docs/adr/0021 is partly superseded.** Its reasoning — cap the Aggregation Units, truncate L4 all-or-nothing, spend per-cell bytes only on what cannot be derived — still governs the payload unchanged. Only its transport claim is dead: the payload is no longer returned inside `job.data` and is no longer read through `GET /jobs/{jobId}`. The write it describes was in fact already deleted in `7f717636` ("Removed statistics async job temporary PoC outputs"), which left `runDescriptiveStatistics` computing statistics and discarding them until this change.
- **A payload big enough to outgrow a single response is now a schema problem as well as a response problem**, since `data` is a jsonb column read whole. The escape hatch 0021 names — spill to storage and return a presigned path, as `export` does — remains the answer, and remains an API change.
