# External Models run on Model Runners that pull their Runs from the core

**Status:** Accepted. Amends ADR 0053: `soil_index_type` is no longer a closed enum.

A **Model** computes a **Soil Index** outside the core, on a **Model Runner**: a service written in any language and run as any number of instances, which registers itself with the core and works only once an operator approves it. The runner pulls its work. Its instances claim waiting Soil Index **Runs** from the core, read each Run's Units and inputs from the core, and send back scores or an error. The core keeps owning the Run (its record, its attachment, its cancellation, finalizing and tiles), so everything that reads a Soil Index Run today works unchanged. The core never calls a runner.

## How it works

- **Registration and approval.** A runner registers itself with `POST /model-runners`, sending its id, name, public key and first Manifest in a JWT signed with the key it registers, whose public half travels in the JWT's `jwk` header. The registration starts pending: the runner's Frameworks are invisible, it gets no Runs and reads no data, and its other calls get 403. A super-admin approves it with `POST /model-runners/{id}/approve`, deciding whether it may read Observations, and can later disable it. A pending registration does not reserve its id: approving one drops the others for the same id, and one left unapproved expires after 7 days. Registration is rate-limited and caps the number of pending entries, because it is the one call no known runner has signed.
- **Registry.** A table, `model_runners`, with one row per runner: its id, name, state (pending, approved or disabled), whether it reads Observations, its public keys, its latest Manifest, and the last time the core heard from each instance. A public `GET /model-runners` lists the approved runners and their Manifests, without keys.
- **Keys.** A runner adds a key with `POST /model-runners/{id}/keys`, signed with a key it already has, and removes one the same way. A super-admin can remove any key, for example after a leak.
- **Runner calls.** Every call carries a JWT the runner signs with its private key: ES256, `typ: model-runner+jwt`, `iss` set to the runner id, `aud` set to `CORE_PUBLIC_URL`, `exp` at most 5 minutes away, and an `instance` claim naming the pod. The token validator reads `typ` before `kid`. Runner routes refuse Plugin tokens and user tokens, and no other route accepts a runner's JWT.
- **Manifest.** The runner publishes its **Manifest** to the core with `PUT /model-runners/{id}/manifest`, and the core checks it against a schema. It lists the runner's Frameworks and Models: each Model's id, version, texts, official classes, hover fields, and required inputs, each met by one or more soil properties in order of preference. The core refuses a submission naming a Model the Manifest does not list. It takes the Run's soil properties from the Manifest, never from the caller, and records them on the Run.
- **Model ids.** `{runnerId}/{modelId}`, which is also the `soil_index_type`, so one runner can never fill another runner's Runs. An id is kept across versions while the scores keep their meaning; a new method or new thresholds make a new Model. Every Run records the version it ran.
- **Claims.** A claim is atomic (`FOR UPDATE SKIP LOCKED`), so two instances never get the same Run. It carries a 10-minute lease that each progress call renews. Every later call names the claim: a call on a claim whose lease lapsed gets 409, and a call on a destroyed Run gets 410. A Run fails after its 3rd lapsed claim, or after 24 hours unclaimed.
- **Inputs.** Only through the claim's inputs endpoint, in `/soil-data`'s row format and paging. The core reads them as the submitter: their local Entitlements, worked out fresh on each read, the `preview` Capability as `/soil-data` and the core's own Runs use it, every criterion of the Run's Filter, the Run's Units through its derived Filter, and only the soil properties recorded on the Run. A Dataset the submitter cannot preview is left out, not refused.
- **Served Datasets.** The core records which Datasets it served for each Run. That record, never the runner's **Provenance**, is what a check on private Datasets reads.
- **Results.** Either scores, in numbered chunks the core checks line by line and stages in the Run's unattached partition, with the Provenance; `complete` then hands the Run to a finalize job on the `soil-indexes` queue, which narrows the scores to the sampling dates (ADR 0058), numbers them, attaches the partition, writes the record and queues the tiles. Or an error: a code (`insufficient-data`, `invalid-inputs`, `model-error`), a message for users, and details. A sample the Model skips is listed in the Provenance and does not fail the Run.
- **Liveness.** Every runner call counts as a heartbeat, written at most once a minute per instance. A runner is available while the core has heard from it in the last 5 minutes, silent after that, and disabled once an operator disables it. Only an approved, available runner gets new Runs. Silence never removes a runner.
- **Polling.** A `204` from `POST /claims` carries `Retry-After`, 5 seconds to start, so the core sets the pace of every runner. A runner that just finished a Run claims again at once.
- **Limits.** Each is an environment variable: the lease (10 min), attempts (3), the wait before an unclaimed Run fails (24 h), silence (5 min), the JWT's lifetime (5 min), the `Retry-After` value (5 s), a score chunk (10,000 lines or 10 MB), metadata per score (4 KB), an input page (5,000 lines), scores per Run (1,000,000, above which the upload fails with `too-many-scores`), and the life of an unapproved registration (7 days).

## Considered options

- **Push: each runner serves an API, and the core submits, polls, fetches and cancels.** This is crea-index-service's current contract. It gives faster cancelling, no polling delay, and a path to OGC API - Processes. Rejected because every runner would build and host a job API with its own queue and job store, each Run would live in two places that can disagree, and the core would make outbound calls, which ADR 0065 avoided. crea-index-service limits the exposure by running models on the core's internal network with no authentication, which works for one first-party model but not for runners hosted elsewhere. A service that speaks OGC API - Processes can still join through an adapter that pulls Runs from the core and calls it.
- **Runners as Plugin Backends (ADR 0065).** A plugin has one Plugin Backend and one token audience, so every runner would accept the same tokens, and a Plugin token is read-only and lasts 5 minutes.
- **A run token on the existing `/soil-data` routes.** This is how crea-index-service reads data today. Rejected because three routes would learn a new kind of token and check the Run's Filter on every call, and `/soil-data` cannot narrow to the Model's soil properties.
- **A catalog file at a URL the browser fetches.** Every runner would need a public host with CORS, and the core could not check submissions against what the runner offers.
- **The runner's own `datasets_read`.** A buggy or careless runner could leave a Dataset out.
- **A config item the operator edits by hand.** An earlier draft of this design. `PUT /configs/{configId}` replaces the whole item with no version check, so a save from an old copy could bring back a removed key, and operators would copy public keys by hand. The `theme` row was ruled out for the same reason: theme pages save the whole object from a cached copy (ADR 0055).
- **Registration with no approval.** Anyone could put Frameworks in front of every user, receive users' Observations, and claim a runner id that every stored score then carries.
- **Shared API keys, or a `jwksUrl` per runner.** Keys would make the core store secrets. A `jwksUrl` would make the core fetch an address the runner chooses.

## Consequences

- `soil_index_type` accepts the core's enum or `{runnerId}/{modelId}`. The core still computes its built-in `crea-index` mock, and dashboards built on it keep working.
- crea-index-service changes contract. Its `POST`, `GET` and `DELETE /runs` and the re-attach and back-pressure logic in `registry.py` give way to a worker that claims Runs, `fetch_samples` reads the inputs endpoint in one call, it publishes its Manifest at startup, and its `variant` parameter becomes three Models.
- **Left open for the dashboard access feature.** A Soil Index Run's id is still the whole permission to read its scores (ADRs 0039 and 0044), so the tiles and the per-score endpoint do not check the served Datasets. When the rule that every viewer of a dashboard must be entitled to its private Datasets is built, it should apply to those reads as well.
- Limiting a Model to some users, if it is ever needed, is an Entitlement (a `models` scope with a `run` Capability), never a list kept on the registry entry.
- A score's metadata can carry values read from private Datasets, for example CREA's measured soil properties. That is covered by the same access rule, not by a limit on what Models may write.
