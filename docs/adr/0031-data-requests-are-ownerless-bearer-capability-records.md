# A Data Request is an ownerless, append-only record whose id is the capability

`data_requests` (`id`, `request`, `data`) keeps an answered data request and the payload that answered it, because the pg-boss job that produced it is deleted on retention and the answer has to outlive it. The row carries **no owner, no `created_at`, and no status**: it is not a job store, not a **Filter**, and not a cache. An identical `request` inserts a new row rather than reusing one, so the table is a record of answers given, and rows are only ever fetched by `id`.

The absence of an owner is the whole design, and it makes the id a bearer capability: holding the id is the entirety of the authorisation to read the payload. That is why `id` defaults to `gen_random_uuid()` and not the `uuidv7()` used by every other table in this schema — uuidv7 embeds a millisecond timestamp and a counter, so ids minted near each other are correlated and partly predictable, which is fine for a primary key sitting behind an authorization check and wrong for a token that *is* the check.

## Consequences

- **A stored payload freezes an entitlement decision at the moment it was computed.** CONTEXT.md has a job resolving Entitlements under the **Subject** that submitted it, and docs/adr/0027 has a **Purge** destroying Entitlements outright — neither reaches a `data_requests` row. Anyone who obtains the id reads what the original caller was entitled to, at the time they were entitled to it. Distributing the id is distributing the data.
- **`data` is the payload inline and unbounded.** This deliberately reintroduces what ADR 0021 capped — an uncapped cross product in a jsonb column — now with the `crea-index` Unit cap removed in front of it (docs/adr/0030). jsonb's hard ceiling is 1 GB per value and TOAST is the only thing between here and it; a row that large is also a single HTTP response. The alternative was an envelope pointing at a `crea_index` Run or a presigned storage key, which is the pattern ADR 0021 recommends; it was not taken, so a size ceiling has to come from the producing code or not at all.
- **Nothing can be swept, attributed, or audited.** With no timestamp and no Subject there is no answer to "how old is this row", "who asked for this", or "delete everything belonging to X". Adding any of those later is a schema change plus a backfill that has no source to backfill *from*.
- **No dedup is what keeps the ownerless design safe.** Deduplicating identical requests across callers — the `raster_footprints.geom_hash` pattern is right there, and Filters already dedupe by canonical content identity per docs/adr/0007 — would hand one caller's stored payload to another through a shared id. Filters can dedupe because they dedupe *per owner*; this table has no owner to scope it to.
- **No index on `request`.** Rows are reached by primary key only. A GIN index would make "every request that touched dataset X" answerable, and is the obvious thing to add first if this table ever needs to be analysed rather than just read back.
