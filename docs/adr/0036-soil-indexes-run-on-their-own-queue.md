# Soil Indexes run on their own queue, and the half they share with Data Requests becomes a Run

A `crea-index` Run costs far more, and for entirely different reasons, than a `descriptive` one, and both were dispatched from the one `data-requests` queue capped at `localConcurrency: 1`. One index Run therefore blocked every data request behind it for as long as it took. We split the Soil Index Types onto their own `soil-indexes` queue, and extract everything the two kinds of Run share — entitlement re-derivation, Filter resolution, Aggregation Unit extraction, the unit cap, cancellation and progress — into `jobs/runs/`, named for the **Run** that both queues execute.

This reverses the reasoning recorded in `processDataRequest`'s docstring, which argued that one queue should serve every product because "a queue per type would duplicate [the shared half] or force a shared library that is a pipeline in all but name". That argument still stands on its own terms and is not being called wrong — it simply never weighed head-of-line blocking, which turned out to be the binding constraint. The library it predicted does now exist; the answer to its objection is that the pipeline has a name, **Run**, and a glossary entry, so it is a domain concept rather than an accident of factoring.

## Consequences

- **`statistics_type: "crea-index"` is gone from the wire** and is now a `400`. Free to do, because the feature had not been deployed to any environment. **Statistics Type** survives with one member rather than being deleted, because more of both kinds are coming — so `data-requests` keeps its dispatch map and its "parameters this type does not use are rejected" branch, temporarily guarding a single case.
- **Naming the product is required on both queues.** `soil_index_type` is required from the start — defaulting it would enshrine "CREA is the normal one" in a queue built to be generic — and `statistics_type` was made required to match, dropping the `descriptive` default it had carried for backward compatibility. A Run that cannot say which product it computed is answerable for nothing, and the symmetry means one rule to document instead of an exception. Both are enums in the OpenAPI spec, so a missing or misspelled product is rejected by the request validator before any handler runs. The cost: every existing caller of `data-requests` must now send `statistics_type`, which is a breaking change to a queue that had been shipped — accepted because the alternative was a permanent asymmetry between two queues that are otherwise identical up to the product.
- **The stored score carries its own type.** `crea_index` is renamed `soil_index` and gains a `soil_index_type` column. A Run's id outlives its pg-boss job record by design (30-day retention vs. permanent partitions), so once the job row is gone the table name was the only thing left saying which methodology produced a `value` — a guarantee a generic queue destroys. The column restores it at ~8 bytes a row, without a separate runs table.
- **Raster masking became a property of the type, not of unit resolution.** Each registered type declares `appliesRasterMask`, and the shared preamble sets `raster_filtered = appliesRasterMask && hasRasterFilters(...)` and writes `derived_filter_id`, `unit_count` and `units[]` exactly once. This was previously duplicated per producer and justified by a side effect that, on inspection, was never a side effect of resolving units at all. The documented promise that every Run writes those three fields is now structural: a new type gets it by existing.
- **Raising `data-requests` concurrency is a separate decision from this split, and does not follow from it.** The `localConcurrency: 1` cap existed because the `descriptive` producer runs two `TEMP` staging tables with `work_mem = 512MB` for its percentile aggregates — a Postgres memory constraint. Moving index Runs away frees a worker slot and **zero** database memory. Concurrency therefore rises to 5 only in exchange for `work_mem` falling to `128MB`, holding aggregate sort memory roughly where it was; both are env-driven (`DATA_REQUESTS_CONCURRENCY`, `DATA_REQUESTS_WORK_MEM`) so the trade between them is tunable in one place. Individual Runs spill to disk sooner under contention. Both figures are **per node** and nothing sets a pg-boss group key, so `JOB_GROUP_CONCURRENCY` does not bound the total across pods.
- **`soil-indexes` starts at `localConcurrency: 1`**, env-overridable. What a real CREA Run consumes is not yet known — the current implementation is `mockIndexValue` — and the cost is reported to be per-Run rather than per-Aggregation-Unit, so the resource it contends for cannot be inferred from the cap that already exists.
- **Nine `DR_*` error codes become `RUN_*`**, since they are raised by the shared extraction and would otherwise tell a Soil Index user to "start the data request job again". Codes never cross the API boundary — clients see only the translated message, and an unknown code hits `FALLBACK` — so no consumer breaks. `DR_DATASET_NOT_ENTITLED` and `DR_UNKNOWN_STATISTICS_TYPE` stay, being genuinely descriptive-only.
- **One unit cap governs both queues** (`MAX_AGGREGATION_UNITS`, with `DATA_REQUESTS_MAX_UNITS` honoured as a deprecated fallback). A per-queue override was considered and rejected: the CREA index's cost does not scale with unit count, so there is nothing yet to tune apart.
- The queue is `soil-indexes`, never `indexes`, because the **DAI** is also an index and is computed on `refresh-dai-stats`. Under the shorter name, the DAI's absence would need explaining forever.

## Considered options

- **Keep one queue and raise its concurrency** — the smallest change, but it makes head-of-line blocking a tuning problem rather than removing it, and a slow index Run would still occupy a slot sized for the memory profile of a fast one.
- **Split the queue but let `soil-indexes/` import from `data-requests/`** — the smallest diff, rejected because the coupling would be directional and invisible: the index queue would depend on the internals of a sibling queue's folder, which is worse than either sharing a named module or duplicating outright.
- **Split the queue and duplicate the preamble** — honest independence, rejected because the duplicated parts are the entitlement re-derivation (ADR 0022) and cancellation semantics, which are precisely the parts most damaging to get subtly different between two copies.
- **Retire Statistics Type and give each product its own queue and vocabulary** — cleaner on paper, rejected because further Statistics Types are planned; the axis is not vestigial, it is early.
