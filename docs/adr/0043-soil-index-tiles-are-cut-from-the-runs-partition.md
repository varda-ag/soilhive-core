# Soil Index map tiles are cut from the Run's partition, not from a view

MVT tiles for a Soil Index Run are generated by PostGIS from the Run's own `soil_index` partition and served by the backend. There is no DB view, no tile-creation job and no DB function. The partition is already the materialized, indexed, immutable table a view would be, and the Run that writes it is already the async job. The year range and **Year Window** are applied in the browser from each tile feature's `year`, so no parameter is left to build a view from.

- **`soil_index_runs`** holds one row per Run, written in the same transaction as the partition `ATTACH`. For tiles it holds the bounds and the detail zoom; ADR 0044 makes it the Run's whole record. This reverses ADR 0036's "no runs table": that ADR saved one column, and now there are several facts with nowhere else to live.
- **The detail zoom** is computed inside the Run, before `ATTACH`. It is the first zoom where no tile exceeds the aggregation budget. Below it, tiles carry per-(grid cell, year) summaries (mean, min, max, count) instead of Scored Geometries, each drawn as one point at the centroid of the scores it summarises.
- **Tiles over the pre-render budget** are rendered by an internal follow-up job into `soil_index_tiles`, gzipped, with one partition per Run. As with `soil_index`, an attached partition means the work is done.
- **Both budgets count vertices, not features** (`ST_NPoints`). For points the two are the same. For polygons, vertices are what a tile costs (as ADR 0006 found for UserGeometries). Both budgets are env-configurable and independent.
- **One MVT layer, `scores`, at every zoom, with one attribute set:** `value` (float4; a cell's mean) and `year`, plus `count`, `min` and `max` on cells only. Absent means no value, as in ADR 0021. For a Run that scores points, one `circle` style then works at every zoom; one that scores polygons also needs a `fill` layer above the detail zoom.
- **Scored Geometries gain an `id`,** numbered 1..n within each Run at write time, with `(run, id)` as the primary key. Existing partitions are backfilled. It becomes the MVT feature id, which MapLibre's `feature-state` needs for hover highlighting. Cells take ids from a range that can't collide with row ids.
- **Metadata is fetched on hover, not embedded in tiles:** `GET /soil-indexes/{runId}/scores/{id}` returns the row's `metadata`, immutable and formatted in the browser. Embedding it would put bytes the vertex budget doesn't count into every tile. Fetching keeps tile size governed by the budget alone, and needs no cap on metadata size.
- **Tile URLs carry a tiling version** (`/soil-indexes/{runId}/tiles/{version}/{z}/{x}/{y}`), listed by a TileJSON served with a short `max-age`. Tiles are immutable, so a browser never re-fetches one. Bumping the version is the only way a change to how tiles are produced reaches clients that already cached them. Pre-rendered tiles are stamped with the version that rendered them, and only the current version's are served. Otherwise, after a bump, a tile pre-rendered at the old version would be cached under the new URL for good. The same happens when a worker still running the old code pre-renders during a rolling deploy. A stale tile is cut on request instead, without the pre-render bound, until its Run is pre-rendered again.
- **`GET /soil-indexes/{runId}/tiles` is TileJSON-shaped, with relative `tiles` paths,** like every other path the backend hands out, because the backend doesn't know its public origin. A host hook resolves the paths against `BACKEND_BASE_URL` and returns a MapLibre source. Plugin Context exposes the same hook as `useSoilIndexTileSource(runId)`. Plugins submit, poll and delete Soil Index Runs through hooks mirroring the Data Request ones (ADR 0044).
- **The tile route lives in Express:**
  - it sits outside `transactionMiddleware` and runs one cancelable pooled query (`runCancelableQuery`);
  - concurrent tile queries are capped per node, configurable by env;
  - the Run id is the whole permission (ADR 0039), so responses are `Cache-Control: public, immutable`.

## Considered options

- **A view per request, built by a tile job (the original brief).** Every parameter is either fixed by the Run or applied in the browser, so the job would rebuild what the partition already is.
- **Martin or pg_tileserv.** Parameterised layers, the detail-zoom switch and the stored-tile lookup would all have to be DB functions. It also adds a service, plus an auth proxy once private tiles arrive.
- **Cells drawn as their squares.** At 1/64 of a tile, about 8 px, a Run zoomed out looked like a coarse raster, which then jumped to dots at the detail zoom. The cell's centre would instead draw a regular lattice of dots.
- **One real score per cell, with its own value.** It would colour a whole cell by one arbitrary score, and hovering it would show that one score's metadata for a feature standing for many.
- **H3 cells at low zoom.** H3 runs only in JS (`h3-js`). A tile-aligned square grid needs nothing new and never splits a cell across tiles.
- **Subdividing Scored Geometries into a tile-only `soil_index_pieces` table** (deferred). One polygon over the aggregation budget is otherwise shown as a cell at every zoom, and pre-renders every tile it touches. The pieces can't live in `soil_index`, because statistics count one row as one score (ADR 0039). This is deferred until a real methodology produces such polygons. Three safeguards keep adding it later cheap: the tiling version above; one data-layer function that both the detail-zoom pass and the tile query read geometries through; and an env-configurable cap on pre-rendered tiles per Run, above which the follow-up job stops and the remaining tiles are cut on request.
- **Owner-only or config-attached tiles.** Both need a token on every tile request and a Plugin Context change, since plugins never see the token. Deferred until a dashboard actually has to be private, which is additive in the way ADR 0041 was.

## Consequences

- A tile cut on request never reads more than the pre-render budget. That bound is what makes an unauthenticated tile endpoint safe, as the cache does for the routes in ADR 0028. A Run that hits the pre-render cap loses the bound for its remaining tiles. That is the case the deferred pieces table exists to fix.
- A tile URL is a bearer capability: sharing the map shares the scores.
- Destroying a Run is housekeeping, not revocation. It removes the server's copy of the scores and tiles, but `public, immutable` tiles already held by a browser or a shared cache outlive it. A Run id is never reused, so such a copy is never wrong, only kept. Revoking access to scores is the deferred private-tiles work, not deletion.
- Tiles for Features are out of scope and need their own design. Three of this design's assumptions fail for them:
  - access to their data is checked per caller (Visibility and Entitlement), not per URL;
  - a snapshot of their Observations would outlive a Purge;
  - Bulk Loads, Archives and Purges change what a tile should show, so tiles can't be immutable.
  The route, budgets, cell aggregation and pre-rendering carry over; the privacy and lifecycle model doesn't.
- A future delete of a Run drops two partitions and one row.
