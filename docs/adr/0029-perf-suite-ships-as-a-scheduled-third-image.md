# The performance suite ships as a third image, whose container invalidates three of the local runner's assumptions

The performance suite (`scripts/perf/runner.ts`) was built for a developer's machine: a git checkout, a `.env` file, a persistent `perf-results/` directory and one `NODE_OPTIONS` for both the runner and the server it spawns. Running it on a schedule against a deployed environment means packaging it as an image — a third build alongside the backend and frontend — and **every one of those four assumptions is false in a container**. This ADR records the packaging choice and, more importantly, the assumptions it breaks, because three of them were themselves deliberate decisions with their own recorded rationale (ADR 0024, ADR 0028, and the header comment on `publish.ts`).

The image is `soilhive-core-perf`. Its Dockerfile lives at `backend/src/scripts/perf/Dockerfile`, beside the code it packages, but its **build context is `backend`** — the two are deliberately not the same directory. It supports both of the suite's modes; which one runs is decided at runtime by `PERF_BASE_URL` alone, exactly as on a developer machine. The container runs the suite **once and exits**; the schedule lives in the orchestrator, not in this repo, which holds no deployment manifests for the other two images either.

A scheduled Perf Run is a **measurement followed by a comparison**: the container runs `runner.js` and then `diff.js`, because a latency number with nothing to compare it against is not a regression signal. That second step is what turns the image from a thing that produces files into a thing that produces an alarm, and it is the source of most of the changes below — a diff was previously only ever run by hand, against a directory of accumulated local runs.

Vocabulary: the artifact is the **perf image**, one execution is a **Perf Run** (the name `types.ts` already gives it), and the schedule produces **scheduled Perf Runs**. It is *not* a "third deployment" — "deployment" already means a customer's SoilHive install throughout `docs/infrastructure.md`, and this is a scheduled job, not a third application container. `infrastructure.md`'s statement that SoilHive is composed of two application containers remains true and is deliberately left unchanged.

## Considered options

- **Using `backend/src/scripts/perf` as the build context**, as first proposed — rejected because it is impossible, not merely awkward. The context is the only thing sent to the daemon, and that directory holds five `.ts` files: no `package.json`, no `tsconfig.json`, no `src/`, and no `tests/assets/geojson`, which `runner.ts` resolves as `BACKEND_ROOT/tests/assets/geojson` and without which every row aborts. Such a Dockerfile could only do `FROM` the published backend image, and could still not `COPY` the assets, because they lie outside the context. The path itself is perfectly legal — `docker/build-push-action` takes `context` as a free-form string — which is precisely why the impossibility is worth recording: nothing rejects the configuration, the build just cannot express what it needs to. Keeping the Dockerfile in the perf folder while pointing the context at `backend` required one new optional `file` input on `docker-build-reusable.yaml`, since the action defaults `file` to `{context}/Dockerfile`.
- **`FROM ghcr.io/.../soilhive-core-backend:<tag>` plus the assets** — rejected despite being the DRY option, and it is the one a future reader will propose. It would prove the perf image contains the same runtime as the backend it measures, at the cost of ~60 duplicated lines. But it serialises the perf build behind the backend build, and it **breaks outright on fork pull requests**: `docker-build-reusable.yaml` only pushes when `head.repo.full_name == github.repository`, so on a contributor's fork there is no tag to pull. This is an open-source repo with a contributor gate; fork PRs are a normal case, not an edge one. The accepted cost is drift between the two Dockerfiles' shared parts — the pinned `NODE_VERSION` digest, the `gdal gdal-tools gdal-driver-pg` line, the deps stage.
- **Adding `tests/assets/geojson` to the backend image and overriding only the CMD** — rejected: 7.2 MB of perf fixtures would ship to every production backend, and a third image would still be needed to change a default.
- **Reusing zero-argument `perf:diff` after hydrating the newest *N* runs from S3** — rejected, though it was tempting because it would leave every pairing rule in `findLastTwoRuns` and add no selection code at all. The failure mode is that the bucket is shared: local developer runs, other environments and both cache modes all publish to the same prefix, so the newest *N* files can easily contain no run matching this target and cache mode while a perfectly good baseline sits at *N+1*. The diff would then fail on a bucket that holds exactly what it needs.
- **Calling the diff from inside `runner.ts`** behind a flag — rejected: `diff.ts` runs `main()` at module scope and owns `process.exit(1)` in its catch, so importing it means refactoring the module and changing the local `perf:diff` path to serve a container concern. Two processes chained by an entrypoint preserves the separation the two npm scripts already express.
- **A second schedule for the diff** — rejected: racy (how long after the run?), doubles the schedules to maintain, and the diff would have to *find* the run that just happened instead of being handed it.
- **An in-image cron daemon** — rejected: it would duplicate scheduling the platform already provides, with no retry, overlap or deadline semantics, and a hung run would silently block every later one.
- **Building the perf image on `main` and tags only** — rejected: the sole way to validate a change to the container's behaviour would be to merge it first, which is a poor loop for a job that runs unattended and can fail quietly. It is wired to the same gate, triggers and dual-arch matrix as the other two, and pays two extra builds and a third PR comment for that.

## Consequences

- **The shell-versus-`.env` distinction that ADR 0024 and ADR 0028 call load-bearing simply ceases to exist, and this is accepted.** Both ADRs justify their read ordering by *where a value is visible*: `PERF_BASE_URL` and `PERF_CACHE_BYPASS` are read before `dotenv` so they are "visible in the command and in shell history", while `PERF_CACHE_BYPASS_SECRET` is read after it so a production credential never enters that history. A container has neither a shell history nor a `.env` — `dotenv` silently no-ops on the missing path — so every knob arrives through `process.env` and the ordering, while still executing, no longer discriminates between anything. The guarantees are re-established by different mechanisms rather than abandoned: the *visibility* of the measured target comes from the CronJob spec being a reviewed, version-controlled artifact, and the *secrecy* of the bypass secret comes from supplying it as a secret reference rather than a literal env value. A perf image whose bypass secret is pasted into a manifest as plain text has lost ADR 0028's protection, and nothing in the code can detect that.
- **`publish.ts`'s "best effort" no longer means what its comment says, so the container demands more.** Its rationale for never failing a run on a failed upload is that "the artifacts are already on local disk at this point" — true on a laptop, false in a pod, where `/app/perf-results` dies with the container and a warning line is all that survives. `PERF_REQUIRE_PUBLISH=true`, set in the image, makes a failed upload fail the run **and** makes a missing `STORAGE_MODE=s3` a precondition failure that aborts *before* anything is measured, rather than after ten minutes of work that cannot be recorded. The default stays best-effort, so the local contract is unchanged.
- **The runner and the server it measures need different heap limits, which required a code change.** `startServer` spawns `dist/app.js` with `env: process.env`, so the child inherits the parent's `NODE_OPTIONS`; the backend image runs production on `--max-old-space-size=256`. Sharing that cap would either measure a non-production heap (if raised) or risk an OOM in the runner, which parses all 7.2 MB of assets up front and holds every response body per row (if kept). An OOM there would abort a long, expensive run near its end and look like a perf problem rather than a tooling one. `PERF_SERVER_NODE_OPTIONS` now overrides `NODE_OPTIONS` for the spawned child only, so managed-mode numbers stay production-faithful — which is managed mode's entire justification.
- **`gitSha`, `gitBranch` and `gitDirty` come from build args in the image.** All three are required fields on `Fingerprint`, but `diff.ts` never compares them — they name result files and head the HTML reports. `git` is absent from the image and `.dockerignore` excludes `**/.git`, so `runner.ts` falls back to `PERF_GIT_SHA`/`PERF_GIT_BRANCH` when the `git` call fails, and records `gitDirty: false`, which is true by construction: an image is built from a committed tree. This is also the semantically correct value — ADR 0024 notes the sha describes *the suite*, and in a container the suite is the image.
- **The image bakes no measurement defaults.** `ENV` is limited to what holds regardless of schedule (`PERF_GIT_*`, `PERF_REQUIRE_PUBLISH`, `PERF_SERVER_NODE_OPTIONS`, `NODE_OPTIONS`, `NODE_ENV`); `PERF_BASE_URL`, `PERF_ASSETS`, `PERF_ITERATIONS`, `PERF_ENDPOINT` and `PERF_CACHE_BYPASS` come from the schedule, and so does the alerting policy — `PERF_DIFF_FAIL_ON_REGRESSION` and `PERF_DIFF_FAIL_THRESHOLD` are not baked either, because whether a regression should page someone belongs to the schedule that decided what to measure, not to the image. So the CronJob spec is the single readable answer to "what does this run measure?", with no invisible image-level default silently contradicting it. The cost is that an unset `PERF_ASSETS` means the full suite: 24 asset/params combinations × ~8 rows ≈ 190 measured rows, each `PERF_ITERATIONS` requests with a 120 s per-request timeout. The orchestrator's deadline, not the image, is what bounds that.
- **A run with failed rows still exits non-zero, so the job is marked Failed — deliberately.** A row that 502s or times out is the regression the schedule exists to catch. This requires `backoffLimit: 0`: a retry would be another full run against the same target, and under `PERF_CACHE_BYPASS` a deliberately load-generating one. Both result files are written and published before the non-zero exit, so a failed job still leaves a complete record.
- **The container reads from the results bucket as well as writing to it, which is a new direction of dependency for the suite.** `findLastTwoRuns` reads only the local `perf-results` directory and throws when it holds fewer than two files; an ephemeral pod has exactly one, the run it just wrote. So the baseline is selected by walking the S3 `perf-results` listing newest-first, downloading and parsing candidates until one matches the current run's `pairingKeyOf` (target + cache mode), skipping unparseable or version-mismatched files exactly as the local backwards walk does, and bounded by `PERF_DIFF_LOOKBACK` so a bucket full of other targets' runs cannot become an unbounded download. The pairing rules themselves are *not* reimplemented — `pairingKeyOf` is reused — but the selection walk now exists twice, once over a directory and once over a bucket, and a change to what makes two runs comparable must be made in both. Hydrated baselines are written to `perf-results/` and deliberately never re-published, so a diff cannot clobber the run it read.
- **"No baseline" and "cannot read the bucket" are different outcomes, and only one of them fails the job.** A successful listing that yields no matching run is a benign no-op: the diff is skipped and the container exits on the run's own code. This is the normal state of the *first* scheduled run of any pairing, and of the first run after `PERF_BASE_URL` changes, `PERF_CACHE_BYPASS` flips, or `PERF_RUN_VERSION` is bumped — none of which are errors. A listing or read that *fails* exits non-zero, symmetrically with `PERF_REQUIRE_PUBLISH` on the write side. Collapsing the two would let a revoked IAM permission masquerade as a fresh start indefinitely, which is discovered only by going looking for diffs that were never produced.
- **The diff now decides an exit code, which it never did before, and it needs a second threshold to do so.** `diff.ts` prints `REGRESSION` lines and exits 0 today; a scheduled job that always succeeds produces no signal. `PERF_DIFF_THRESHOLD` keeps its existing job of classifying rows for the report, and a new, higher `PERF_DIFF_FAIL_THRESHOLD` decides the exit code, because raising the single existing knob to stop a noisy job from flapping would also degrade the report that knob exists to render. `newlyFailing` rows — succeeded in the baseline, error now — fail regardless of latency, being a binary signal rather than a measurement. Failing on regressions is opt-in and off by default, so local `perf:diff` is unchanged. The noise floor is real and is the operator's problem to tune: `PERF_ITERATIONS=1` makes a "median" a single sample, and ADR 0024 records that consecutive attached-mode iterations may land on nodes in different cache states.
- **The entrypoint runs the diff even when the run failed, and combines the two exit codes.** `runner.js && diff.js` would skip the comparison precisely when it is most informative, since `newlyFailing` is exactly what a run with failed rows produces. But failed rows and an *aborted* run are indistinguishable by exit code, and an abort writes no result file at all — so the entrypoint gates the diff on **the presence of a result file**, not on the run's exit code, and skips it with a plain message when there is nothing to compare. It keeps the runner's code, and exits non-zero if either step did. The consequence is that a job's failure no longer says *which* step failed; the logs do, and both steps publish their artifacts before exiting.
- **`npm run perf` and `npm run perf:diff` are both unusable inside the image**, and this is easy to trip over when editing the Dockerfile. The first runs `npm run build` first (no `tsc`, since dependencies are installed with `--omit=dev`); the second runs `ts-node --transpile-only` (also absent). The entrypoint invokes `node dist/scripts/perf/runner.js` and `node dist/scripts/perf/diff.js` directly. A future change to those npm scripts will not reach the container.
- **In managed mode the container needs database credentials, and that is a privilege the other two images' cron equivalents would not need.** `runner.ts` aborts when it cannot read row counts for the fingerprint, and `getDBPassword`/`getSSL` require either `POSTGRES_PASSWORD` or `POSTGRES_AWS_REGION` plus an IAM role, with the RDS trust bundle read from `dist/assets/global-bundle.pem`. Attached mode needs none of it. A schedule that only ever measures a deployed target should therefore not be given credentials at all.
