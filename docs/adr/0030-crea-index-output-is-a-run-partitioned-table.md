# CREA index output moves out of job data into a table partitioned per Run

docs/adr/0021 capped soil-statistics input at 200 Aggregation Units because the whole result had to fit in the pg-boss `job.data` jsonb and one HTTP response, and named moving the output out as the way to lift that ceiling. The `crea-index` **Statistics Type** is taking that route: its aggregation is being reimplemented without the Unit cap, and its scored geometries now land in a `crea_index` table (`run`, `geometry`, `value`, `metadata`) partitioned `BY LIST (run)` with one partition per **Run**, created and ATTACHed by the job. `crea-index` is the first of these, not the exception: every Statistics Type's output is to move out of job data the same way, and ADR 0021 is amended to say so. Until `descriptive` follows, it still resolves Units through the capped path and everything ADR 0021 describes still governs it.

Partitioning is per Run rather than hashed or absent because a Run is write-once and then read-only, which makes the partition boundary the retirement boundary: discarding a Run becomes `DROP TABLE` instead of a bulk `DELETE` over an unbounded row count. HASH would have avoided runtime DDL entirely but leaves retention as a delete-and-vacuum problem and buys little over a plain btree on `run`; RANGE is not available at all, because `run` is a pg-boss `gen_random_uuid()` v4 with no ordering in it.

## Consequences

- **The write landed before any reader did, and job data says nothing about it.** `crea-index` now contributes no output key whatsoever — not the FeatureCollection, not a count — because the Run id *is* the job id, so a caller able to poll the job already holds everything it needs to find the rows; a count would only restate what it used to look them up. No endpoint serves the table yet, so the only way to read a Run's scores today is to query the database. This was accepted knowingly rather than overlooked: the storage move and the read path are separate pieces of work, and the frontend never consumed `job.data.crea_index`, so nothing regressed when the key went away. The one thing genuinely lost is a completed Run's row count at a glance — it survives only as prose in `progress_description`.
- **The Unit cap is still in the code.** Removing it is part of reimplementing the aggregation, which has not happened yet; `runCreaIndex` still calls `extractUnits` and still throws `SST_TOO_MANY_UNITS`. Until that lands, this table holds at most 200 rows per Run and the partitioning is provisioned for a load it is not yet carrying.
- **`run` carries no foreign key, by necessity.** pg-boss lives in `${POSTGRES_SCHEMA}_pgboss` and deletes its job rows on its own retention timer, so the referent is guaranteed to vanish while these rows remain. A Run id is therefore readable long after there is anything left to ask about its progress — which is what the **Run** entry in CONTEXT.md is there to warn about.
- **Retention is deferred, and this is known debt rather than an oversight.** LIST partitioning degrades plan time once partition count reaches the low thousands, so partitions must eventually be swept. Nothing today records when a Run happened: `run` is a v4 uuid with no embedded timestamp, the pg-boss row that had one is deleted, and the table has no `created_at`. Whoever adds the sweeper has to add one of those three first — a `created_at` column, a run registry table, or a timestamp in the partition name.
- **Partitions are created by application code, not by this migration.** The parent ships with no partitions. The low-lock path is to build the partition standalone, load it, create its GiST index, and then `ATTACH` (`SHARE UPDATE EXCLUSIVE` on the parent since PG12) — `CREATE TABLE … PARTITION OF` takes `ACCESS EXCLUSIVE` and would serialise concurrent Runs against each other. Creating the index before the ATTACH matters too, or the ATTACH pays for the build while holding its lock.
- **No primary key and no `unit_id`.** Rows are anonymous facts read back in bulk. This drops the traceability `jobs/soil-statistics/types.ts` insists on — that the Feature `id` is the `unit_id` and "the only way back to the area", because equivalent geometries in a source file collapse into one Unit and positional correspondence does not exist. Under the reimplemented aggregation that path back must live in `metadata`, which is why `metadata` is `NOT NULL DEFAULT '{}'` and load-bearing rather than an optional extra.
- **`geometry(Geometry,4326)` is deliberately untyped.** A scored unit is a Point for some products and a Polygon/MultiPolygon for others, so nothing in the schema tells a reader which to expect. The representative-point machinery in `creaIndex.ts` — `ST_Centroid` when it falls inside the geometry, `ST_PointOnSurface` otherwise, so a marker never lands in the gap between disjoint parcels — becomes a per-producer choice rather than a property of the type.
- **The only index is GiST on `geometry`**, declared on the parent so it propagates. Partition pruning covers access by Run; a btree on `value` was left out until a threshold or ranking query actually exists, since within one Run's partition a sequential scan may well win.

## Considered options

- **HASH on `run`, fixed partition count** — no runtime DDL, no lock or privilege concerns, constant plan time; rejected because retention returns to `DELETE` + vacuum and a single large Run still lands wholly in one partition.
- **No partitioning, btree on `run`** — simplest thing that works, and defensible while volume is moderate; rejected because with the Unit cap gone there is no bound on a Run's row count and no cheap way to retire one.
- **Keeping the FeatureCollection in `job.data` alongside the table** — nothing downstream would have changed, at the cost of duplicating an output that is now explicitly allowed to be large.
