# Identity is the Subject, not the token `sub`

Everything that records or authorises a caller — `datasets.created_by`, `files.created_by`, `data_mappings.created_by`, the `entitlements` table's `id`, and (as of SP-5521) a job's `created_by` — is keyed by the **Subject** (`getSubject`, `src/utils/auth.ts`). This is a deliberate inversion of the usual advice to key on the stable opaque `sub`, and jobs were the last place still keying on `sub` directly.

The Subject forks on the kind of caller rather than on which claims a token happens to carry:

- a **Machine caller** — one whose `gty` claim names the `client_credentials` grant — is its `client_id`, and any `email` on the token is ignored;
- every other caller is its `email`, else its `sub`.

The fork replaced a single unconditional chain (`email ?? client_id ?? sub`). That chain assumed only a machine would ever present a `client_id`, which is false: an interactive login carries the app's own client id too, so on a deployment whose IdP omits `email` from access tokens — the case this ADR already flagged below — *every* user of the app collapsed into one shared Subject. They pooled each other's Entitlements and wrote indistinguishable `created_by` rows.

## Considered options

- **Subject, email-first (chosen).** Entitlements are granted by data admins through `PUT /datasets/{id}/entitlements`, where the id they type is a person's email — nobody knows a colleague's OIDC `sub`. Keying on the Subject means the grant, the audit trail (`created_by`) and the enforcement check all agree without a lookup table mapping emails to subs, and it keeps every `created_by` column legible to a human reading the database.
- **Token `sub` throughout (rejected).** Stable across email changes and never spoofable, but it makes grants unusable in practice: an admin would have to discover an opaque identifier before granting access, and every existing row would need migrating. It also does not help the `client_id` case, where there is no meaningful per-user `sub` at all.
- **`client_id` unconditionally, before `sub` (rejected — the original chain).** One flat chain, no grant claim to depend on, and it worked on every IdP. It is unsound for the reason above: `client_id` identifies *which application asked*, not *who asked*, so it can only stand in for an identity when there is no person behind the request — and nothing in the chain established that. Kept here because the shape is the obvious one to reach for again.
- **Widening the machine branch beyond `client_credentials` (rejected).** A service-account token renewed through the refresh-token grant carries `gty: refresh_token`, so its Subject flips from the `client_id` to an opaque `sub` mid-session. The rule is still not widened: `refresh_token` is equally what a silently-renewed *interactive* token carries, so the claim alone cannot separate the two, and the second signal it would take (no `email`, or the presence of Keycloak's `clientHost`) is exactly the guesswork this decision removes. Keycloak does not issue refresh tokens for the client-credentials grant by default, so the case only arises if a deployment turns that switch on. Auth0's hyphenated `client-credentials` is not matched either, for the same reason: no deployment needs it yet, and an untested branch in the identity chain is worse than an absent one.
- **`azp` as a fallback for a missing `client_id` (rejected, for now).** Identical in value on Keycloak's tokens and emitted by more providers, but it names the authorized party rather than the requesting client, and the two only coincide in the single-audience case. Add it when a deployment actually needs it.
- **A first-class user table mapping sub → email (rejected as premature).** The correct long-term answer if emails ever need to change while grants survive, but it introduces a user-provisioning concern the platform does not otherwise have.

## Consequences

- **A caller whose kind cannot be established is treated as a person.** Most IdPs emit no grant claim at all — Auth0 and Keycloak do, a generic RFC 9068 access token does not — so on those deployments a Machine caller keys on its `sub` rather than its `client_id`, and any Entitlement already granted to a client id there stops matching and must be re-granted. That is the deliberate direction of failure: an unrecognised machine loses legibility and needs one re-grant, whereas guessing the other way merges distinct people into a single identity, which is a security boundary rather than an inconvenience. `docs/authentication.md` documents the claims an IdP must emit and what breaks without each.
- **An unverified `email` claim confers Entitlements.** The trust boundary is the identity provider: if it issues a token with an attacker-chosen `email`, that token inherits every Entitlement granted to that address. The `email_verified` claim is present but not enforced anywhere. Acceptable only because the IdP is trusted to issue truthful email claims; it must be re-examined before federating additional providers.
- **Changing a user's email revokes their access** and orphans their `created_by` rows, until an admin re-grants under the new address. There is no rename path.
- **A job runs under the Subject of its submitter.** `JobService.createJob` writes `created_by` via `getSubject`, and job ownership on read/cancel compares against the same value. Before SP-5521 jobs wrote `sub` here and then looked entitlements up by it, so no per-user row ever matched and every processor collapsed to `everyone`'s Entitlements — private Datasets the submitter was entitled to were silently skipped, and explicitly named ones failed the job with `SST_DATASET_NOT_ENTITLED` after the API had already accepted the request.
- **Jobs enqueued before this change are keyed by `sub`** and are therefore no longer matched by their submitter's ownership check. Given pg-boss retention this self-corrects; no migration is provided.
- **The external entitlements endpoint remains invisible to processors**, which have no raw token. Aligning the key fixes local Entitlements only; a Subject whose access is exclusively external still sees Datasets skipped in implicit mode. That gap is documented at `runDescriptiveStatistics` and unchanged here.
- **An IdP that omits `email` from access tokens makes every grant unreachable**, because the email branch of `getSubject` never fires and every caller resolves to its `sub` (or, for a **Machine caller**, its `client_id`). Nothing fails: `PUT /datasets/{id}/entitlements` accepts the rows, stores them keyed by the addresses typed, and no token ever matches one. The Admin console's dataset settings page therefore gates its access-grant form on the **access token's own `email` claim**, decoded client-side, and warns rather than hiding so the misconfiguration is actionable by whoever can fix it. The id_token/userinfo `email` (react-oidc-context's `user.profile.email`) is **not** a valid proxy and must not be substituted: the `email` scope's defined effect is to populate the id_token, while emitting `email` in the access token is a separate IdP-specific claim mapping — so `profile.email` is typically present on exactly the deployments the gate exists to detect, and using it would turn the check into a false reassurance. `email_verified` is deliberately not consulted either: the gate mirrors `getSubject`, and requiring verification there would disable a working feature on most deployments without moving the trust boundary described above. Closing that gap remains a backend decision with a migration story.
- **`BulkLoader` does not benefit yet**: it reads `created_by` off the pg-boss `Job` wrapper rather than `job.data`, so it resolves `undefined` regardless of what `createJob` writes. Tracked separately.
